What this repo is

swe-pro-agents is not an application — it is a pack you install into OpenCode. It ships the "brains" of a software-engineering agent team:

Agent profiles

26 markdown system prompts — an orchestrator, architecture & review roles, a researcher, and 19 domain subagents.

Skills

25 reusable workflow definitions, auto-discovered by OpenCode from ~/.config/opencode/skills/.

CLI

swe-pro-agents run drives plan execution headlessly; setup wires config.

Plugins

Thin OpenCode adapters: idle nudge, background delegation, probe spawn.

EOS

AGENTS.md — the Engineering Operating System every agent follows.

Installer

Copies agents/skills/plugins; a manifest makes uninstall safe.

Install copies files into ~/.config/opencode; it never overwrites a user's own AGENTS.md — it places a package-scoped copy and tells the user to merge or reference it.

Architecture at a glance

The design is a hybrid: a JSON ledger + a plugin session.idle nudge + a conductor agent + a <promise>DONE</promise> completion token + an optional headless CLI. The plugin is the only "magic" — and it is a nudge, not logic. Every decision lives in testable code.

The execution loop

Two modes share the same ledger and the same budgets (2 attempts/task, 40 iterations/run, stop-on-blocked).

Plugin mode (interactive)

  1. User starts swe-pro with a plan: "execute plans/tasks.md".
  2. swe-pro inits the ledger, then runs the conductor loop per task: validate → syncWithSpec → shouldContinue → markInProgress → dispatch a fresh subagent → verify → applyAttemptResult (atomic save) → end with <promise>DONE</promise>.
  3. Session goes idle → swe-pro-agents.js fires. It returns immediately unless: agent is swe-pro, the session has an active goal (armed via /goal), the ledger is running, no task is in_progress, and a task is pending. Then it resumes swe-pro.
  4. Stops on: all done, a task blocked (2 failures), budget exhausted, or a gate trip (paused).

CLI mode (headless)

  1. swe-pro-agents run --plan plans/tasks.md loads/inits the ledger and loops.
  2. Each iteration spawns opencode run <msg> --agent swe-pro --format json, scans raw stdout for the promise token, records the result, saves atomically.
  3. Exit 0 = done; 1 = blocked/paused/budget; 2 = usage error. The child is told not to touch the ledger (CLI is the single writer).

Fail-closed: no /goal ever executed (or a plugin restart lost in-memory arm state) → the loop never activates on idle alone. CLI mode is already command-activated.

The /goal feature flag (shipped)

This is the work merged in PR #20. The entire /goal + continuation system is now a separable, opt-out unit toggled by a project config flag.

  • swe-pro-agents.config.json with { "features": { "goal": true } } at the project root. Default on, fail-open (missing/corrupt config ⇒ enabled).
  • When disabled, the plugin stays installed but inert: it registers no /goal command and ignores idle events.
  • The flag is re-read on every idle (not cached at load), so flipping it takes effect without restarting OpenCode.
  • /goal show / status / help are neutral — they report state without arming or disarming (previously show armed the gate).
  • swe-pro-agents setup --goal|--no-goal (or an interactive [Y/n] prompt) writes the flag; --apply also writes the opencode.json entry.
  • Single source of truth: scripts/pack-config.js owns read+write for the CLI; the plugin inlines its own copy (OpenCode plugins can only require sibling files).

R6 risk (documented, not fixed): setup writes to process.cwd() while the plugin reads OpenCode's directory. If they differ, the flag fails open to true and silently has no effect — mitigated by docs ("run setup from the project root").

Background subagents (PR #19, merged)

Delegate coding tasks to background subagents with git-worktree isolation, concurrency, priority, and crash recovery.

plugins/swe-pro-agents.js   (tools: bg_delegate/read/status/list/stop/steer/prune)
        │ inlined
        ├─ delegation engine         (state machine, journal, terminal-state protection)
        ├─ background-spawner seam     (SessionSpawner; NativeSpawner = stub for future)
        ├─ background-scheduler        (per-model concurrency + fair-share + backpressure)
        ├─ background-supervisor      (liveness probes, backoff restart, quarantine, CB)
        └─ background-worktree        (isolation)  +  background-results (schema + redaction)

Data flow: bg_delegate → registered → scheduled → running (worktree created, child spawned) → supervisor polls for completion → on terminal, result is written + journaled → bg_read returns it → parent runs bg_merge --check (conflict report only; never auto-merges).

Non-goals (binding): no auto-merge, no native manager.launch() dependency in v1, no tmux, no cross-machine distribution, no new runtime dependencies.

Design principles (from EOS)

Hybrid, not monolithic

Ledger + plugin nudge + conductor + promise token + CLI. The hook is a nudge, not logic.

Single writer

CLI owns the ledger headless; swe-pro owns it interactive. No dual writers.

Fail-closed / fail-open

No goal ⇒ no loop (closed). Missing config ⇒ feature on (open).

Zero deps

Node CJS, built-ins only. No supply-chain surface.

Atomic & validated

tmp+rename writes; validateState on every load; schema version rejected on mismatch.

Plain-node tests

No framework. npm test chains every suite; CI runs Linux+Windows × Node 18/20/22.
